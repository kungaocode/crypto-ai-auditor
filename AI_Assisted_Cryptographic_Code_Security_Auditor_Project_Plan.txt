AI-Assisted Cryptographic Code Security Auditor
AI辅助密码代码安全审计系统——详细项目计划书

一、项目基本信息
项目名称：
AI-Assisted Cryptographic Code Security Auditor

中文名称：
AI辅助密码代码安全审计系统

项目定位：
构建一个结合静态程序分析、密码安全规则、大语言模型（LLM）和Agent机制的密码代码安全审计系统，用于识别常见密码误用、分析漏洞上下文、进行CWE分类、风险评估并生成修复建议。

项目目标：
1. 建立密码误用（Cryptographic Misuse）数据集。
2. 建立可扩展的密码安全静态分析规则库。
3. 实现“代码 → 静态分析 → LLM → 安全报告”的完整Pipeline。
4. 将Qwen3-4B作为基础模型，先进行Zero/Few-shot Baseline。
5. 使用QLoRA进行密码安全领域适配，比较微调前后的效果。
6. 引入Agent机制，实现静态分析结果的上下文理解、二次验证和误报过滤。
7. 通过系统实验比较不同架构的检测能力。
8. 最终形成GitHub项目、技术报告、Demo和可写入CV/PS的AI项目经历。

五、第一类数据：CWE标准数据

主要来源：
MITRE Common Weakness Enumeration（CWE）。

重点关注：
CWE-321  Hard-coded Cryptographic Key
CWE-327  Broken or Risky Cryptographic Algorithm
CWE-328  Reversible One-Way Hash
CWE-329  Predictable IV with CBC Mode
CWE-330  Insufficiently Random Values
CWE-338  Weak PRNG
CWE-326  Inadequate Encryption Strength
CWE-759  One-Way Hash without a Salt
CWE-916  Insufficient Computational Effort

获取字段：
- CWE ID
- Name
- Description
- Common Consequences
- Potential Mitigations
- Detection Methods
- References
- Related weaknesses

保存为：
data/raw/cwe/
cwe_database.json

数据用途：
1. 建立漏洞标签体系。
2. 为规则设计提供标准。
3. 为LLM Prompt/RAG提供知识。
4. 为最终CWE分类评估提供Ground Truth。

注意：
CWE数据主要作为标准知识和标签来源，不应简单复制网页全文作为训练数据。

六、第二类数据：Semgrep规则

主要来源：
- Semgrep Community Rules
- 其他公开安全规则仓库
- 自己设计和实现的规则

处理方式：
Existing Rules
→ 理解规则逻辑
→ 筛选密码相关规则
→ 根据项目需要重新实现/定制
→ 建立自己的crypto_rules目录

目录：
rules/
├── weak_algorithm.yaml
├── weak_mode.yaml
├── hardcoded_key.yaml
├── weak_random.yaml
├── predictable_iv.yaml
└── tls_misconfiguration.yaml

第一版建议实现10类规则：

CRYPTO-001  MD5
CRYPTO-002  SHA-1
CRYPTO-003  DES / 3DES
CRYPTO-004  RC4
CRYPTO-005  AES-ECB
CRYPTO-006  Predictable IV
CRYPTO-007  Hard-coded Key
CRYPTO-008  Weak Randomness
CRYPTO-009  Weak Key Length
CRYPTO-010  Insecure TLS Configuration

每条规则建议包含：
- rule_id
- name
- cwe
- severity
- languages
- patterns
- description
- recommendation
- references

示例：

id: CRYPTO-005
name: AES ECB Mode
cwe: CWE-327
severity: HIGH
language: Python
pattern: AES.MODE_ECB
description:
  Detect use of AES in ECB mode.
recommendation:
  Use an appropriate authenticated encryption mode such as AES-GCM.

七、第三类数据：Synthetic Vulnerable/Secure Code

这是项目自己的核心数据。

为每种密码误用构造：
- Vulnerable Code
- Secure/Improved Code
- CWE
- Severity
- Explanation
- Recommendation

示例：

Vulnerable:
cipher = AES.new(key, AES.MODE_ECB)

标签：
CWE-327
Severity: HIGH
Finding: AES-ECB mode

Secure/Improved：
cipher = AES.new(key, AES.MODE_GCM)

注意：
不能简单认为“替换成另一个算法”就是安全修复。
例如密码存储中不能机械地把MD5替换为SHA-256，而应考虑Argon2id、scrypt、bcrypt等专用密码哈希/KDF方案。

第一阶段目标：
10类漏洞 × 50~100个样本
≈ 500~1000个Synthetic samples。

数据生成方式：
1. 手工编写典型样例。
2. 对代码模板进行参数化变换。
3. 改变变量名。
4. 改变代码结构。
5. 加入不同上下文。
6. 生成同一漏洞的多种实现形式。
7. 使用LLM辅助生成候选代码。
8. 最终人工审核。

LLM生成的数据不能直接视为Ground Truth，必须人工或规则验证。

八、第四类数据：真实开源代码

目标：
使用真实开源项目检验系统，而不是只测试人工构造代码。

候选项目：
- Python cryptography projects
- C/C++ cryptographic projects
- TLS implementations
- Authentication systems
- Open-source security projects
- Encryption libraries

获取流程：
GitHub Repository
→ 下载/Clone
→ 固定commit/version
→ 提取.py/.c/.cpp等文件
→ Semgrep扫描
→ 筛选密码相关Finding
→ 人工确认
→ 保存代码上下文和标签

第一阶段：
10~20个开源项目即可。

每条真实样本记录：
- repository
- commit
- license
- file path
- language
- code snippet
- line number
- finding
- CWE
- severity
- verification status

注意：
必须保留数据来源和许可证信息。
不要使用来源不明的数据集。
不要直接复制第三方数据并声称为自己构建。

十、数据清洗与验证

Pipeline：

Raw Data
→ 去重
→ 代码规范化
→ 删除无关代码
→ 标签统一
→ CWE映射
→ Severity统一
→ 人工验证
→ 数据分割

检查项目：
1. CWE是否正确。
2. Finding是否真实存在。
3. Vulnerable/Secure标签是否正确。
4. 修复建议是否合理。
5. 是否存在重复样本。
6. Train/Test是否存在代码泄漏。
7. 同一仓库的高度相似代码不要随机拆到Train和Test中。

这一点非常重要：
如果同一个项目的相似代码同时出现在训练集和测试集，会造成数据泄漏，使模型表现虚高。

十二、模型训练策略

不建议一开始就训练。

分三个阶段。

Stage 1：Base LLM Baseline

模型：
Qwen3-4B

输入：
代码 + Static Analysis Finding

输出：
Security Analysis

Pipeline：
Code
→ Semgrep
→ Finding
→ Qwen3-4B
→ Security Report

记录Baseline：
- CWE Classification
- Severity Classification
- Explanation
- Recommendation
- False Positive Triage

Stage 2：QLoRA Fine-tuning

使用项目已有的Qwen3-4B QLoRA训练经验。

训练格式：

Input:
Language: Python
Static Finding: AES-ECB detected
Code:
cipher = AES.new(key, AES.MODE_ECB)

Output:
CWE: CWE-327
Severity: HIGH
Root Cause: ...
Security Impact: ...
Recommendation: ...

训练流程：
Dataset
→ Tokenization
→ QLoRA
→ Qwen3-4B
→ Validation
→ Checkpoint
→ Test

目标不是把模型训练成“密码专家”，而是研究：
Domain-specific fine-tuning是否能够提高LLM对密码误用的分析能力。

Stage 3：Agent

加入工具调用和二次验证。

Agent流程：
Code
→ Static Analysis
→ Candidate Finding
→ Agent Observation
→ Context Analysis
→ Tool Action
→ CWE Check
→ Risk Check
→ False Positive Check
→ Final Report

Agent可以调用：
- Semgrep
- AST parser
- Crypto rule database
- CWE knowledge base

十三、Agent设计

Agent采用Observation-Action思想。

Observation：
- Source code
- AST
- Static analysis result
- Relevant code context

Reasoning：
- 判断是否真的使用了密码功能
- 分析数据流/上下文
- 判断Finding是否成立
- 判断CWE
- 判断风险

Action：
- 调用Semgrep
- 查询规则
- 查询CWE
- 请求代码上下文
- 生成修复建议

最终：
Verification:
CONFIRMED / REJECTED / UNCERTAIN

十四、False Positive过滤

这是系统的重要功能。

示例：

Semgrep：
AES-ECB detected

Agent：
→ 检查代码上下文
→ 判断ECB实际用途
→ 判断是否为测试代码
→ 判断是否处理敏感数据
→ 检查是否存在额外安全机制
→ 输出：
Confirmed / False Positive / Needs Review

因此项目不只是：
LLM解释漏洞

而是：
LLM-assisted security finding triage。

十七、Evaluation指标

1. Detection Accuracy
是否发现问题。

2. CWE Classification Accuracy
是否正确分类。

3. Severity Accuracy
风险等级是否合理。

4. False Positive Rate
误报率。

5. Explanation Quality
人工评价：
Correct / Partially Correct / Incorrect

6. Recommendation Correctness
修复建议是否正确、安全。

7. Patch Validity（可选）
如果生成Patch：
- 是否能运行
- 是否真正消除问题
- 是否引入新问题

二十二、项目安全边界

本项目定位为防御性安全研究。

主要目标：
- Cryptographic misuse detection
- Secure coding analysis
- Vulnerability triage
- Security recommendation

不以：
- 自动攻击真实系统
- 自动生成恶意利用代码
- 自动攻击第三方服务
作为项目目标。

真实代码测试应优先使用：
- 本地代码
- 自己编写的测试程序
- 明确允许分析的开源项目
